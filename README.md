# AI-Assisted Carrier Invoice Reconciliation
# 承运商账单自动核对与数据质量校验

> 用**合成账单 + 真实物流底表**搭建的一条对账链路：把物流承运商账单逐条核对回内部系统记录与费率表，
> 识别差异、量化金额影响、按根因归类，并用 AI 工具沉淀可复用的校验规则与 prompt 模板。
>
> 零第三方依赖（纯 Python 标准库），`python3` 直接可跑；另附 BigQuery 版本 SQL。

---

## 业务背景

跨境 3PL / 电商的财务团队每月会收到承运商账单，需要逐条核对回自己的内部系统记录。
现实痛点是：

- **量大人少** —— 一张账单几千到几万行，人工核对成本高、漏检多
- **差异类型多** —— 未入账 / 重复计费 / 计费重量不对 / 费率用错 / 金额加总错误，每种的处理方式都不同
- **争议难举证** —— 跟承运商交涉时，要能说清「应付口径是什么、差在哪、影响多少钱」

本项目把这条链路做成一个**可运行、可量化、可演示**的对账工具：

| 能力 | 实现 |
| --- | --- |
| **应付口径唯一** | 账单生成与核对**共用同一套计费逻辑**（`src/rating.py`），从根上消除"两套口径" |
| **按根因归类** | 5 条规则按优先级排列，同一笔差异只归一个根因，**不重复计算金额** |
| **金额可量化** | 输出「多收应追回 / 少收待确认 / 净影响」三类金额，可直接交给财务跟进 |
| **效果可评估** | 有 ground truth，能算出**查全率与查准率** |
| **规则可复用** | 沉淀 5 个 prompt 模板；AI 输出必须**回源验证**才可采用 |

### 承运商账单（合成）

**真实的承运商账单是商业机密，公开数据集里不存在。** 所以本项目的做法是：
以「内部记录 + 费率表」为应付真相，**反向合成**账单，并按真实世界的差异类型注入错误。

这样做有三个好处：

1. **底表可以是真实数据**（Olist），不是玩具数据；
2. **我们知道 ground truth**，因此能算出查全率 / 查准率 —— 这是用现成数据集做不到的；
3. **更贴近现实**：现实里拿到的账单本来就没有标注，异常检测本就要自己定义规则、自己判断。

## 5 条校验规则

| 规则 | 名称 | 判定逻辑 | 典型根因 |
| --- | --- | --- | --- |
| **R1** | 未入账 | 内部有发货记录，账单中查无此运单 | 承运商漏开票 / 数据丢失 |
| **R2** | 重复计费 | 同一运单在账单中出现 > 1 次 | 系统重复推送 / 人工重复录入 |
| **R3** | 计费重量偏差 | 相对偏差 > 5% 且绝对差 > 0.05kg | 体积重计费 / 称重误差 |
| **R4** | 费率不符 | 分区不一致，或各项费用与费率表不符（容差 1%） | 用错分区 / 用错重量档 |
| **R5** | 金额加总错误 | 行总额 ≠ 各项费用之和（容差 $0.05） | 账单生成逻辑缺陷 |

**计费公式**（账单生成与核对**共用** `rating.py` 的同一套逻辑，避免"两套口径"）：

```
小计   = base_rate + per_kg_rate × 计费重量
燃油费 = 小计 × fuel_surcharge_pct
应付   = 小计 + 燃油费 + remote_surcharge
```

## ⭐ 双实现交叉验证：本项目最有价值的部分

同一套规则，我写了**两套完全独立的实现**：

| | 实现 | 范式 |
| --- | --- | --- |
| **A** | `src/reconcile.py` | Python 过程式（逐条遍历、按优先级 classify） |
| **B** | `sql/reconcile_duckdb.sql` | DuckDB 集合式 SQL（`CASE` 优先级 + 窗口函数） |

对账系统最怕的不是"算错"，而是**不知道自己算错了**。两套不同范式的实现跑同一份数据、
要求输出逐字段一致 —— 这是最经济的一致性验证手段：同一处逻辑 bug 很难在两套实现里同时出现。

```bash
python3 validate.py     # 跑 SQL 版并与 Python 版逐字段比对（退出码可用于 CI）
```

### 交叉验证抓到的六个真实问题

这套机制**真的抓到了 bug**，而且一个比一个深：

#### 问题 1｜两套实现对「舍入口径」的理解不一致 → 13% 的行差 0.0001

本项目把**应付口径**定义在 `src/rating.py` 里，而且是**逐项舍入**：

```
续重费 = round(单价 × 计费重量, 4)
小计   = round(基础费 + 续重费, 4)
燃油费 = round(小计 × 燃油费率, 4)
应付   = round(小计 + 燃油费 + 偏远附加, 4)
```

SQL 版最初写成**对整个表达式一次性舍入**：

```sql
ROUND((base_rate + per_kg_rate * 重量) * (1 + 燃油费率) + 偏远附加, 4)
```

**两者公式完全相同，但结果不同** —— 因为**舍入是非线性运算，位置一变结果就变**：

| | 逐项舍入 | 一次性舍入 |
| --- | --- | --- |
| 结果不同的行 | — | **14,624 / 112,650（13.0%）** |
| 单行最大差额 | — | 0.0001 |
| 净差 | — | 0.7222 |

> ⚠️ 注意措辞：在**没有舍入的实数域**里两者恒等，但**一旦中间有舍入就不再等价** ——
> 所以不能说"数学上等价，只是精度问题"。舍入位置本身就是口径的一部分。

**性质是「口径分歧」，不是「算术错误」** —— 一次性舍入本身算得没错，
它错在**没有遵守项目已经定义的应付口径**。对账系统最该先消除的就是这类问题：
**不是算错了，而是两边对"怎么算"的理解不同。**

**教训**：对账系统必须先明确「应付金额在哪里舍入」并写进文档 —— 这不是实现细节，是**业务口径**。

> 📌 **一个必须诚实交代的点**：本项目**为什么**选逐项舍入？
> 理由是真实承运商账单通常**逐项列示**（基础费 / 续重费 / 燃油附加分开列，各自取整到分），
> 复刻账单口径时必须逐项处理。
>
> 但要说清楚：**这是基于账单结构的合理假设，不是从真实账单里验证出来的** ——
> 真实账单是商业机密，本项目拿不到（这也是为什么账单要"反向合成"）。
> 正因为口径是**假设**而非**事实**，就更必须把它**显式定义在一处**（`rating.py`）并写进文档，
> 而不是散落在某段代码里。对账前第一件事永远是：**双方确认口径一致**。

#### 问题 2｜严重度分档踩到浮点边界 → 差一个档位

```
运单 SHP2026001841：billed 26.5647 − expected 25.5647
Python 得到的差值：0.9999999999999964  → 判为 low
SQL   得到的差值：1.0                 → 判为 medium
```

两个数都无法被 IEEE754 精确表示，相减后略小于 1。
**修法**：金额按「分」取整后再分档（`round(x, 2)`）—— 1e-15 级的差异是浮点噪声，不是真实金额差。

#### 问题 3｜用二进制浮点做金额计算 → **2 万行里 1,198 行（6%）结果错误**

这是最严重的一个，也是最经典的一课：

```
真实值（账单上列示的数）：30.051945
IEEE754 双精度实际存储：  30.051944999999996   ← 落在 .5 边界下方
round(..., 4)            ：30.0519  ❌   正确应为 30.0520
```

在 SQL 里同时跑 DOUBLE 路径与 DECIMAL 路径对比：

| 路径 | 与 DECIMAL 结果不一致的行数 |
| --- | --- |
| DOUBLE | **1,198 / 20,000（6%）** |
| DECIMAL | 0（基准） |

**修法**：两套实现**全程改用十进制** —— Python 用 `decimal.Decimal` + `ROUND_HALF_UP`
（集中在 `src/money.py`），SQL 用 `CAST(... AS DECIMAL(18,4))`。

> ⚠️ 为什么不用 Python 内置 `round()`：它是**银行家舍入**（round-half-to-even），
> 与 SQL 的 `ROUND()`（四舍五入）在 `.5` 边界上不一致。
> 金融场景统一约定为**四舍五入**，并用 `Decimal` 显式指定舍入模式。

#### 问题 4｜DuckDB 的 `DECIMAL / DECIMAL` 会返回 `DOUBLE` ⚠️方言陷阱

前三个问题是在**合成数据**上发现的。换成 **Olist 真实数据**（11.2 万运单）再跑一遍交叉验证，
又冒出一处 `detail` 不一致：同一个偏差，Python 显示 `17.6%`，SQL 显示 `17.5%`。

排查过程（层层递进，值得记）：

```
① 以为是 printf 的问题        → 单独测 printf('%.1f', 17.55::DECIMAL) 得 17.6 ✅ 排除
② 以为是 DECIMAL 没生效       → 逐步 typeof() 一看：

   step1  ABS(b - w)          0.351000            DECIMAL(18,6)
   step2  ABS(b - w) / w      0.1755              DOUBLE          ← 类型在这里退化！
   step3  100 * (...)         17.549999999999997  DOUBLE
   step4  ROUND(..., 1)       17.5                DOUBLE
```

**根因：DuckDB 里 `DECIMAL / DECIMAL` 的结果类型是 `DOUBLE`** —— 除号一出现就退回了二进制浮点。
所以光把操作数 `CAST` 成 DECIMAL 是不够的。

**修法**：**除法之后必须再 `CAST` 回 DECIMAL**

```sql
ROUND(100 * CAST(ABS(CAST(billed AS DECIMAL(18,6)) - CAST(expected AS DECIMAL(18,6)))
                 / CAST(expected AS DECIMAL(18,6))
                 AS DECIMAL(18,8)), 1)
```

Python 侧对应地也要**先把两个操作数转成十进制再相减**（而不是先做 float 减法再转），
否则 Python 会带着完整浮点精度（`Decimal('0.30699999999999994')`）而 SQL 舍到 6 位，两边仍然对不上。

> 💡 **这一条比前三条更有价值**，因为它说明了两件事：
> 1. **"改用 DECIMAL" 不等于万事大吉** —— 还要盯住每个运算的类型传播；
> 2. **同一套代码要在多个数据集上验** —— 合成数据是整数比、恰好没落到 `.5` 边界，
>    真实数据的自然分布才会踩中。

#### 问题 5｜`_severity` 里一个漏网的 `round(x, 2)` → 换数据集时会翻转档位

严重度分档的写法是「**先按「分」取整，再和 1 元 / 5 元比**」：

```python
a = abs(round(impact, 2))            # ❌ 用的是内置 round()
```

写这行时我以为它和 SQL 的 `ROUND()` 等价 —— 其实**完全不同**：

| 值 | Python 内置 `round(x,2)` | DuckDB `ROUND(x::DOUBLE,2)` | **PostgreSQL `round(x::numeric,2)`** | Python `Decimal(HALF_UP)` |
| --- | --- | --- | --- | --- |
| 1.005 | **1.0** | **1.0** | 1.01 | 1.01 |
| 2.675 | **2.67** | 2.68 | 2.68 | 2.68 |
| 0.995 | **0.99** → 判 `low` | **1.0** → 判 `medium` | 1.00 → 判 `medium` | 1.00 |

**Python 内置 `round()` 是「银行家舍入」，而且在二进制浮点上做**；
PostgreSQL / DuckDB 的定点路径是**先转十进制、再四舍五入**。

差点造成什么后果：如果某个 `diff_amount` 恰好落在 `x.xx50`，
**Python 判 `low`、SQL 判 `medium`** —— 直接破坏"逐字段一致"的结论。
（14,077 条里恰好没踩到，**但这是运气不是保证**。）

**修法**：Python 侧改用 `money.round_cents()`（Decimal + `ROUND_HALF_UP`），
SQL 侧先 `CAST(... AS DECIMAL(18,4))` 再 `ROUND(..., 2)`。

> 💡 **教训**：「金额改用 Decimal」**不是一次性的全局替换**，而是要**逐个运算去查**。
> 这个不起眼的 `round(x, 2)` 躲在「严重度分档」里，很容易被漏掉 ——
> 它能被找出来，是因为我把三个引擎的边界行为并排跑了一遍。

#### 问题 6｜跨引擎移植踩到的三个坑（PostgreSQL vs DuckDB）

为了确认 SQL 版不是"只在 DuckDB 上能跑"，我用 Postgres.app 起了一个**本地临时 PG 15.3**
实例实测（`initdb` + `pg_ctl`，测完即删），结论如下：

| # | 坑 | 表现 | 正确写法 |
| --- | --- | --- | --- |
| ① | **PG 没有 `round(double precision, integer)`** | `round(x::float8, 2)` **直接报错** `function does not exist` | PG 必须 `round(x::numeric, 2)` |
| ② | **`NUMERIC` / `DECIMAL` 不带精度时，默认值因引擎而异** | DuckDB `DECIMAL(18,3)`、BigQuery `NUMERIC(38,9)`、PG 无约束。**实测**：同一段 BigQuery SQL 在 DuckDB 上因费率 `1.1875` 被吃成 `1.188`，**与正确口径差 11,080 行** | **永远写全精度**：`CAST(x AS DECIMAL(18,4))` |
| ③ | **DuckDB 的 `ROUND(double, n)` 是异类** | 它在**二进制值**上舍入：`ROUND(1.005::DOUBLE,2)=1.0`，而 PG `round(numeric,2)=1.01` | 先 `CAST` 成定点数再 `ROUND` |

**跨引擎一致的三条写法**（三者在 .5 边界上结果完全相同）：

```sql
-- PostgreSQL
round(x::numeric, 2)

-- DuckDB（注意：必须 CAST，不能直接 ROUND double）
ROUND(CAST(x AS DECIMAL(18,4)), 2)

-- BigQuery（NUMERIC 默认 38,9，但仍显式写精度）
ROUND(CAST(x AS NUMERIC(18,4)), 2)
```
```python
# Python
from money import round_cents
round_cents(x)        # Decimal + ROUND_HALF_UP
```

> 💡 顺带修掉的一处：`sql/reconcile_bigquery.sql` 原本还是**一次性舍入**（问题 1 的口径），
> 而且 `CAST(... AS NUMERIC)` 没写精度。既然要维护这个文件，就不能让它和主口径不一致 ——
> **同一份口径在三个引擎上必须写成三份能对齐的实现，否则"口径唯一"就是空话。**

### 最终结果

| 数据集 | 运单数 | 差异条数 | 全字段比对 | 不一致 |
| --- | --- | --- | --- | --- |
| 合成（`--source synthetic`） | 20,000 | 2,503 | 2,503 × 13 = 32,539 项 | **0** |
| **Olist 真实（`--source olist`）** | **112,650** | **14,077** | **14,077 × 13 = 183,001 项** | **0** |

```
合成数据   净影响：Python 2,969.65   SQL 2,969.65   差 0.00
Olist 真实 净影响：Python 9,362.84   SQL 9,362.84   差 0.00
```

**两套独立实现在两套数据上都输出逐字段完全一致。**

> 另外用 **PostgreSQL 15.3** 对拍了舍入语义（本地临时实例），
> 并把 `sql/reconcile_bigquery.sql` 的口径也对齐了 —— 现在**三个引擎
> （Python / DuckDB / PostgreSQL / BigQuery 语法）在 .5 边界上写出的是同一个结果**。

## 🔍 项目里最有价值的发现：精度与召回的权衡

`weight_inflated` 的根因归类命中率只有 **75.6%**，这不是 bug，而是**规则设计的一个有意权衡**。

**原因**：R3 除了相对阈值（偏差 > 5%）之外，还加了**绝对差下限 0.05kg**。
对于 0.05–0.3kg 的小件包裹，5% 的偏差只有几克 —— 这在真实称重场景下**属于噪声**，
不应该触发对账告警。代价是：这些小件的重量虚高会被"让"给下一条规则（R4 费率不符）去命中，
于是**根因归类**上算未命中（虽然运单本身仍被标记为异常）。

**三组对照实验**（`--weight-min-delta` / `--weight-pct`）：

| 参数 | 运单级查全率 | weight_inflated 根因命中率 | 说明 |
| --- | --- | --- | --- |
| 默认（pct=5%，min-delta=0.05kg） | 99.17% | **75.6%** | 抗噪优先，小件不误报 |
| `--weight-min-delta 0` | 99.17% | **99.8%** | 召回优先，但真实场景下小件会被称重噪声频繁触发 |
| `--weight-pct 0.20` | 98.69% | **0.0%** | 阈值过松，重量问题几乎全部漏判 |

**结论**：阈值不是"越严越好"。真实落地时要结合**称重设备的精度**和**人工跟进成本**来定 ——
和承运商签合同时，通常会把"允许偏差"写进 SLA，规则阈值应与合同条款对齐。

> 💡 **这一段是本项目最值得读的部分**：它说明这套规则不是"拍脑袋定的阈值"，
> 而是**理解了精度与召回之间的取舍后做出的设计决策**。

### 观察一：Olist 里 1.8% 的订单没有交运日期

**事实**（`data/raw/olist_orders_dataset.csv`，99,441 单）：

| `order_status` | 订单数 | 有交运日期 | 无交运日期 | 无占比 |
| --- | --- | --- | --- | --- |
| `delivered` | 96,478 | 96,476 | 2 | 0.0% |
| `shipped` | 1,107 | 1,107 | 0 | 0.0% |
| `canceled` | 625 | **75** | 550 | 88.0% |
| `unavailable` | 609 | 0 | 609 | 100% |
| `invoiced` | 314 | 0 | 314 | 100% |
| `processing` | 301 | 0 | 301 | 100% |
| `created` / `approved` | 7 | 0 | 7 | 100% |
| **合计** | **99,441** | **97,658** | **1,783** | **1.8%** |

**本项目的处理**：**保留**这 1,783 单对应的运单，发货日期兜底为 `order_purchase_timestamp`
（同一个源表的另一列，未引入外部数据）。

> 为什么不直接过滤掉？「**是否该为未发出的订单计费**」是**业务口径**问题，
> 不该由数据管道单方面决定 —— 管道只负责如实反映、并让口径可被检查。

**如果后续要收紧**，判据该选哪个？这里有个反直觉的结论：

| 判据 | 运单数（`order_items`） | 会漏掉 | 漏多少 |
| --- | --- | --- | --- |
| **A** `order_delivered_carrier_date IS NOT NULL` | **111,456** | `delivered` 但无交运日期的单 | **2** |
| **B** `order_status IN ('delivered','shipped')` | **111,382** | **已交运但被取消**的单 | **75** |

**A 的数量比 B 大（+74），但 A 不是 B 的超集 —— 两者互不包含：**

```
A − B = 75 条   已交运、但最终状态是 canceled
B − A =  2 条   状态是 delivered、但没有任何交运记录
```

所以：

- **别把「A 更大」误解成「A 是 B 的放宽版」** —— A 拿到了 75 条 B 没有的，同时丢了 2 条 B 有的
- **A 更接近业务真相**：`order_delivered_carrier_date` 记录的是「交给承运商」这个**事件本身**，
  而 `order_status` 是**最终状态**，中途会变（发出 → 取消 → 状态变 `canceled`）
- **但 A 也不完美**：那 2 条「已送达却没有交运记录」的订单逻辑上矛盾（送达必经交运），
  属于**源数据缺失**。真实系统里通常要**多字段联合判断 + 人工兜底**

> 💡 这段分析本身就是可讲的素材：**分得清「字段在说什么」和「字段代表什么业务事件」，
> 并且知道任何单字段判据都有边缘情况。**

### 观察二：`service_level` 为什么不从源数据推

Olist 源表**没有服务等级字段**。本项目的处理是**固定为 `standard`**，而不是
用 `freight_value` 去"猜"一个等级 —— 因为：

1. 猜出来的等级**无法验证**（没有 ground truth）—— 会变成"讲不清来源的数字"
2. 货物等级本身是**承运商合同**的产物，公开数据里不存在

代价是费率表里 `economy` / `express` 两档（各 72 行）在 Olist 路径下用不到 —— 这是**有意的取舍**，
换取「每一个数字都能追溯到源数据」。
