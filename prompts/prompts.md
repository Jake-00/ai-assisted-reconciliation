# 可复用 Prompt 模板（5 个）

> 对应 JD 要求：*"Write and refine prompts, **build reusable prompt templates** and lightweight
> AI-assisted workflows for recurring tasks, and **always validate AI output against source data**"*

**使用原则（三条）**

1. **AI 出初稿，人做判断** —— 规则、阈值、结论必须人工评审后才可采用；
2. **所有产出回源验证** —— 抽样核对 AI 的说法与源数据是否一致；
3. **模板要留版本** —— 每次修正后在模板末尾记一行变更原因，下次才不会重复踩坑。

## P1 · 校验规则生成器

**用途**：拿到两张新表（如账单 vs 内部记录）时，快速产出**候选**校验规则清单。
**频率**：每接入一家新承运商 / 新数据源时用一次。

```
你是数据质量与对账领域的专家。下面有两张表的结构与样例数据，
请给出用于「逐条核对」的候选校验规则清单。

【表 A：内部系统记录（应付真相）】
字段：shipment_id, ship_date, dest_zone, service_level,
      actual_weight_g, length_cm, width_cm, height_cm,
      volumetric_weight_kg, chargeable_weight_kg, currency
样例：
{在此粘贴 3–5 行样例}

【表 B：承运商账单】
字段：invoice_line_id, shipment_id, invoice_date, billed_zone,
      service_level, billed_weight_kg, base_amount, weight_amount,
      fuel_surcharge, remote_surcharge, total_amount, currency
样例：
{在此粘贴 3–5 行样例}

【业务背景】
- 计费重量 = max(实重, 体积重)，体积重 = 长×宽×高/6000
- 应付金额 = 基础费 + 续重单价×计费重量，再加燃油附加（百分比）与偏远附加
- 承运商可能出现的差异：重量虚高、用错分区、重复计费、漏开票、金额加总错误

【输出要求】
1. 按「完整性 / 准确性 / 一致性 / 唯一性」四类分组，给出规则清单
2. 每条规则标明：规则名 · 判定逻辑（用可实现的伪代码或 SQL 表达）· 建议阈值 · 可能的误报来源
3. 对每条规则说明：阈值取松/取严分别会带来什么后果
4. 最后列出**你认为需要人工确认才能定的点**（例如阈值、口径边界）

【重要】不要编造字段。只使用上面给出的字段；若某条规则需要额外字段，
请明确写出"需要补充字段：xxx"。
```

**回源验证要点**
- [ ] 抽查 3 条规则，看它在样例数据上是否真的能命中
- [ ] 确认阈值不是我拍脑袋的数字，而是问了业务/合同口径
- [ ] 检查 AI 是否用了不存在的字段（**这是最常见的幻觉**）

## P2 · 差异归因助手

**用途**：拿到差异清单后，产出**根因假设**，指导人工排查。
**频率**：每期账单核对后跑一次。

```
下面是一批账单核对差异。请帮我给出每个差异类型的可能根因假设，
并按「排查成本」从低到高排序，以便我按顺序验证。

【差异汇总】
{粘贴 reconciliation_summary.json 的 by_rule 部分}
{粘贴 5–10 条差异明细}

【已知信息】
- 承运商：___；账单周期：___
- 本期是否有系统变更（如换承运商、改分区表、埋点口径调整）：___
- 历史上出现过的问题：___

【输出要求】
1. 每个差异类型给 2–3 个根因假设，每个假设说明"如何用一句话验证"
2. 按排查成本排序（能直接用数据验证的排前面，需要联系承运商的排后面）
3. 明确指出哪些假设**光靠现有数据无法验证**，需要外部信息
4. 给出建议：哪些差异值得发起争议（附金额），哪些可以接受

【重要】区分「数据问题」和「业务问题」。前者我们自己能修，后者要谈判。
```

**回源验证要点**
- [ ] 每个根因假设都要用源数据实际验证一遍，标注"已验证/不成立"
- [ ] 注意 AI 可能把**相关性当因果**（如"因为换了承运商所以差异变多"）
- [ ] 检查 AI 给出的验证方法是否**真的可执行**（有没有需要但拿不到的数据）

## P3 · 指标口径文档生成器

**用途**：把散落在代码里的计算逻辑，整理成可交付的口径文档。
**频率**：每个新指标 / 每次口径变更时。

```
请根据下面的代码逻辑，生成一份「指标口径说明文档」，
读者是需要理解但不会写代码的财务与运营同事。

【指标清单】
{列出指标名，如：计费重量、应付金额、差异金额、查全率}

【代码逻辑】
{粘贴相关函数或 SQL 片段}

【输出要求】
1. 每个指标一节，包含：业务定义（一句话）· 计算公式 · 数据来源表 · 更新频率 · 边界情况处理
2. 公式用自然语言 + 数学符号各写一遍
3. 标注「易混淆点」：本指标与哪个相近指标容易混淆，区别在哪
4. 最后给出一张"指标 → 负责人 → 上游依赖"的追溯表

【重要】不要改写公式。如果代码逻辑本身有歧义，请标出并提问，不要自行解释成看起来合理的样子。
```

**回源验证要点**
- [ ] 拿文档和代码逐条对：公式有没有被"翻译"错
- [ ] 让不知道背景的同事读一遍，看能不能看懂（这是文档的唯一标准）
- [ ] 检查边界情况（除零、空值、超范围）是否被覆盖

## P4 · 单条差异的业务解释

**用途**：当财务/运营问"这条差异到底什么意思"时，快速产出解释。
**频率**：按需，通常用于金额较大的争议项。

```
请把下面这条账单差异，翻译成财务同事能理解的话，
并给出建议的处理动作。

【差异明细】
{粘贴 discrepancies.csv 中的一行}

【内部记录】
{粘贴对应的 internal_records.csv 一行}

【费率合同相关条款】
{粘贴相关费率行，或说明"参考 rate_card.csv 第 X 行"}

【输出要求】
1. 一句话结论：这条差异是什么性质（多收/少收/待确认）
2. 用"我们原本应该付 X，承运商收了 Y，差 Z"的句式说明
3. 可能的原因（1–2 个，不要罗列一堆）
4. 建议动作：直接争议 / 先核实 / 接受，并说明理由
5. 如果需要联系承运商，草拟一句沟通话术（中英文各一版）

【重要】金额数字必须来自我提供的明细，不要自己重算 —— 如果发现我给的数字自相矛盾，请指出。
```

**回源验证要点**
- [ ] 核对 AI 引用的金额与明细完全一致（**AI 常在此处算错**）
- [ ] 确认建议动作符合公司流程（谁有权发起争议）
- [ ] 沟通话术要经得起对方反驳，别用模糊表述

## P5 · AI 输出验证清单（元模板）

**用途**：**任何** AI 产出在采用前的检查清单。这是本项目的硬性纪律。
**频率**：每次使用 AI 产出后。

```
你刚才产出的内容，请你自己做一遍自查，逐项回答：

1. 【事实核对】你提到的每个字段名、表名、函数名，是否都出现在我给你的输入里？
   如有你自己补充的，请单独列出来。
2. 【数字核对】你引用的每个数字，来源是哪里？是我提供的，还是你算的？
   如果是你算的，把计算过程写出来。
3. 【假设显式化】你做了哪些我没有明确告诉你的假设？逐条列出。
4. 【不确定性】哪些结论你并不确定？给出你的置信度（高/中/低）与原因。
5. 【最可能错的地方】如果这个产出有一处是错的，最可能是哪里？

然后我会用源数据抽样验证你上面的回答。
```

**为什么这个模板最重要**
- 它是**回源验证的抓手**：让 AI 自己暴露假设和不确定点，人工只需要验证这些点，而不是全量复核
- 实践中约 **1/3 的 AI 生成规则**在这个环节被发现阈值不合理或业务上不成立
